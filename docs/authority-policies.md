# Explicit client authority

Workspace membership controls ordinary application access. It does not grant financial approval, delegation or execution. Private intake and provider resources retain their existing owner boundary, including for administrators. Client contacts are facts, not application principals.

In **Client facts → Review authority**, a signed-in owner can inspect their own recorded grants, source references, duties, currency/materiality limits, validity and inactive/revoked history. **Revoke authority** records an explicit reason and applies on the server without another login. Reload checks the current state. An uncertain response blocks another mutation until reload. No grants are seeded in a real installation. Financial operations and actual automated workflow execution are not available in this foundation.

## Root authority and delegation

A trusted local operator must record root authority from an explicit reference using Django's `record_authority` management command in the configured local installation. Required arguments are `--entity`, `--username`, `--action`, `--duty`, `--valid-from`, `--expires`, and `--reference`. Dates must be timezone-aware ISO8601 instants. Monetary actions (`ledger.post`, `payment.release`) additionally require `--limit` as a nonnegative decimal string with at most four decimal places and `--currency` as three uppercase letters. Protected nonmonetary actions (period reopening, vendor detail changes, filing submission and report release) use explicit action/snapshot authority with no fabricated amount or currency. There is no inferred threshold, currency conversion, automatic administrator grant or default approver. A reference records the operator's provenance assertion; it is not independent verification of the underlying document.

`--can-delegate` explicitly permits a human subject to issue one narrower child grant for the same entity, action, duty and currency. A child cannot extend dates, increase the amount, grant authority back to the issuer or delegate onward. Revoking or disabling a parent invalidates the child. An optional `--agent` binds preparer/executor authority to an existing server-owned agent registration for that user and installation. Agents cannot hold reviewer/approver authority or delegate. A provider account alone is not an agent registration.

`revoke_authority --grant <UUID> --reference <withdrawal-reference>` provides trusted local recovery when a subject is disabled or departed. It preserves the original grant, a separate revocation and audit events. These commands require access to the configured installation process and database. They are never browser endpoints or in-app agent tools. Protect that local operating-system account and storage; this policy layer does not protect a database from its trusted operator.

Authenticated human lifecycle endpoints are:

- `GET /api/policies/entities/<UUID>/`: owned entity, current user's grants only, 50-record cursor pages and policy version; no-store.
- `POST /api/policies/grants/<UUID>/revoke/`: exact `reason`, valid same-origin CSRF; subject or recorded delegator only.
- `POST /api/policies/grants/<UUID>/delegate/`: exact `subject_id`, `starts_at`, `expires_at`, `limit`, `currency`, `evidence`; current explicit delegator only. Subject is an existing installation member, not a contact or email inference.

There is no root-authority HTTP endpoint. Actor kind, owner, installation and root provenance are never accepted as authority hints. Membership and agent registration are reread on every check. Financial grants require an enabled non-viewer member; changing membership to viewer, disabling the user or agent, expiry, or revocation denies outstanding work.

## Approval contract

`policies.authority` exposes trusted server factories for humans and registered agents, root provisioning, bounded delegation, preparation, independent review, approval and execution checks. An immutable authorization binds the exact entity and current fact revision, action, record revision, graph/resource identity, canonical payload, amount/currency, evidence, named executor and half-open validity interval. Canonical JSON refuses floats, unsupported types, excessive nesting and oversized content. The preparer's underlying user cannot review or approve their own work, including through an agent identity. Review precedes approval. Attestations retain the exact grant and snapshot hash.

A per-entity policy version changes on grant creation/delegation/revocation. This conservatively invalidates earlier approvals even when a different grant changed. Grant replacement does not rewrite old evidence or silently rescue an expired approval. Every execution check rereads the entity revision, current principals, parent grants, exact attestations and executor. Repeated valid checks reuse the same approval and append an audit decision; they do not create another approval prompt. No audit contains the payload, credentials or raw request. The audit stores the hash, principal, policy version, grant identities, operation and fixed decision code. Authority references and grant metadata remain private application data.

`check_execution` is a policy decision, not a financial operation. `execute` always refuses actual dispatch. Future journal/payment/filing/report adapters must independently validate their domain invariants and calculate materiality from authoritative records, supply current immutable record snapshots, and recheck policy inside their durable execution boundary. A supplied `record_revision` is a hash-bound contract input until that actual record store exists; it is not a claim that a journal or payment was loaded or posted. Proposal UI and real record lifecycle remain separate A03/ledger tasks.

## Workflow contract

The same registry covers workflow discovery/create/edit/triage/run/resume/retry/cancel. Explicit preparer grants cover create/edit; reviewer grants cover discovery/triage; executor grants cover run/resume/retry/cancel. `PolicyResource` records entity, owner, kind (graph/run/job/log/checkpoint), revision, graph identity and parent. All ancestors must remain enabled and share owner/entity/graph identity. A changed graph invalidates its child snapshots. A wrong owner, stale revision or boolean revision denies.

`check_workflow` accepts only dispatch/node/resume stages and rechecks live authority each time. A financial node also needs its exact separate financial approval and matching resource/graph. Preparation captures the persisted resource revision in the approval hash; advancing that revision invalidates the approval even if the graph identifier is unchanged. Workflow run/edit rights do not confer financial approval. Retry accepts only durable not-started or verified-no-effect outcomes. The outcome must come from actual execution evidence, never a caller's guess.

P03 establishes this reusable server policy contract and consumes its membership matrix in existing intake services. It does **not** execute a Fancy Flow graph. A04/A05/A06 must bind actual graphs, runs, jobs, logs and checkpoints to these records, derive protected-node requirements and execution outcomes server-side, recheck on dispatch/node/resume and prove real Python runtime/bridge/tool behavior. Omitting a financial gate is not a supported dispatch adapter. Real provider sessions, agent tools and outward-facing financial operations remain disabled until their own implementation and verification gates pass.
